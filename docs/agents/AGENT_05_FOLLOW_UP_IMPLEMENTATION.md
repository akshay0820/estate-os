Status: **implemented and verified** (2026-10-25). Two limits: **no messaging provider is integrated** (messages are approved and sent by a person, then recorded), and the optional Claude drafting step has never run with a real key. Sections 1–9 are the plan; 10 onward record what was built.

## 2. Data model (additive migration 0014)

- `follow_up_settings` (per org, optional; defaults apply): versioned `rules` jsonb.
- `follow_ups`: one row per planned communication or hand-off.
  - What: purpose, kind (`message` / `task`), channel, consent purpose, reason.
  - Status, schedule, time zone.
  - Content: subject, body, content version + hash, generated by `template` / `ai` / `human`, draft status, model metadata.
  - Facts it relies on: property ids, match run, call, qualification, task.
  - Approval: approver + approved version; rejection.
  - Delivery: sent via, sent at / by, provider message id, attempts, last error.
  - Policy snapshot, idempotency key (unique per org), run id, correlation id.
- **Lifecycle:**
  - `pending_approval` → `approved` (manual send) or `scheduled` (provider connected) → `processing` → `sent` → `delivered` (provider evidence only).
  - Also `failed`, `cancelled` (a person or a material change), `suppressed` (policy blocked: consent, opt-out, do-not-contact), `expired` (not acted on in time), `handed_off` (a CRM task for a person was created or linked).

## 3. Policy engine (`private.fu_policy`) — every outbound check

Evaluated on the **current persisted state** at planning, at approval and again immediately before any send (manual "mark sent" or provider dispatch).

- **Hard blocks** → `suppressed`:
  - org kill switch;
  - lead closed or archived;
  - contact `do_not_contact`;
  - `preferred_contact_channel = none`;
  - no address for the channel;
  - consent for (channel, purpose) not `granted`, or `denied` / `revoked`;
  - a person has asked to handle the lead (open call-back task);
  - shared listing no longer eligible.
- **Defer** → reschedule:
  - outside the messaging window (org time zone, business days, `window` hours);
  - frequency: max per lead per 7 days, minimum hours between automated messages, max consecutive unanswered;
  - cooldown after a human contact.
- **Duplicates:** an active follow-up with the same purpose for the lead.

Claude cannot change any of this.

## 4. Planner (outbox consumer + optional sweep)

| Trigger (persisted state re-read) | Action |
|---|---|
| `property_matching.completed` | Shortlist ≤ `max_properties` current recommendations still active (and verified unless `share_unverified`; unverified ones are labelled "availability to be confirmed"), not rejected or invalidated. With a permitted channel: a **message draft** for approval. Without one: a **task** "Share matched listings" |
| `lead.qualification.needs_information` | Clarification draft: at most `max_questions` questions, only for fields **still missing in the CRM now**. No channel: nothing (Agent 03 already created a clarification task) |
| `voice_call.completed` | Only when the analysed call has unanswered questions: a **task** to answer them. Never a generic "thanks for the call" message |
| `voice_call.human_handoff_requested` | Link Agent 02's call-back task (no duplicate); **cancel** the lead's pending automated messages; new messages are blocked while the task is open |
| `lead.communication_opted_out` | Cancel / suppress pending follow-ups on that channel. Also enforced synchronously by triggers on consent and contact changes, so no event is needed for safety |
| Re-engagement sweep (off by default) | Leads silent for `reengage_after_days` with **marketing** consent, no active follow-up, at most one per period |
| Manual "Suggest follow-up" | Same planner, on demand |

## 5. Messages

- **Template first:** deterministic, from records only (first name, agency name, listing title, locality, price, bedrooms, the availability qualifier, the missing-field questions), plus a fixed opt-out line. A draft is never empty.
- **Claude (optional):** rewrites a pending draft from the same minimal facts. The output is checked, and the opt-out line is re-appended by code:
  - referenced property ids must be the draft's own;
  - numbers must come from the facts;
  - channel length limits;
  - no urgency, scarcity, reservation, confirmation, discount, guarantee or return claims, and no household or demographic wording.

  It can only replace a draft that is still `pending_approval` and unchanged. A human edit makes it `human`. **Approval is bound to the exact content version**; any edit requires re-approval. The model never approves.

## 6. Delivery

- **No provider connected (this project):**
  - approved → `approved` ("ready to send");
  - the person sends through their own channel and clicks **Mark sent**, which re-runs the policy and the content checks first;
  - recorded as `sent` via `manual` with the exact text, a `message` activity, and shared listings marked `shared` in Agent 04.
- **Provider connected** (`integrations` row `connected` for the channel):
  - approved → `scheduled` at the next allowed time;
  - the worker claims due items with a lease after the SQL policy re-check;
  - the adapter sends with the follow-up id as idempotency key;
  - outcomes: `accepted` → `sent`; `transient` → bounded backoff (3 attempts) then `failed`; `permanent` → `failed`; `ambiguous` (timeout after the request left) → `failed` / `ambiguous_outcome` + a task to check, **never retried blindly**.

  No adapter is implemented, because there is no provider: the worker returns `unsupported` and the item goes back to `approved`.

## 7. Events

`follow_up.scheduled`, `follow_up.sent`, `follow_up.suppressed`, `follow_up.human_review_required` (published, ids only, correlation id carried from the trigger). `follow_up.delivered` is reserved for provider evidence and is never emitted without it.

## 8. Security

- Org comes from the outbox row or membership; recipients are resolved from the contact record at send time, never from clients or the model.
- RLS: read with `leads.view`, no client writes.
- Actions:
  - approve / edit / mark sent / cancel / reschedule: `inbox.reply` plus the lead-edit rule;
  - settings: `settings.manage`;
  - service functions: service role only.
- Audit log on every decision.

### Default rules (`follow_up_settings.rules`, all configurable through `follow_up_settings_save`)

| Rule | Default |
|---|---|
| Channel order | WhatsApp → email → SMS (the contact's preferred channel first) |
| Window | 09:00–20:00 in the org time zone, on the org's business days |
| Frequency | ≤ 3 messages per lead per 7 days; ≥ 48 h between messages |
| Unanswered | Stop after 3 unanswered (sent since the last human or call contact) |
| Human cooldown | 24 h after a person's own call / message, a completed call or an appointment |
| Listings shared | ≤ 3, verified only (`share_unverified` false) |
| Questions | ≤ 2, only for fields missing in the CRM now |
| Use cases | Re-engagement **off** (needs `marketing` consent when on) |
| Drafting | Claude drafting on |
| Expiry | Drafts / approved messages expire after 72 h |

High qualification or match scores never raise these limits.

### Decisions this implementation made

- A follow-up is a record of **intent and outcome**. The deterministic planner decides whether a follow-up exists (purpose, channel, listings, questions); Claude can only reword it; a person approves it.
- Share follow-ups are **idempotent per matching run**: the same run never produces a second message.
- Agent 02 already creates call-back tasks. Agent 05 links them (no duplicate task), cancels the lead's pending messages and blocks new ones while the task is open.
- A call with unanswered questions becomes a **task** (the answers need a person), never a generic "thanks for the call".
- No permitted channel for matched listings: a "Share matched listings" task. No permitted channel for clarification: nothing (Agent 03's clarification task already exists).
- Opt-outs from a call (phone) cancel pending messages on every channel for that contact, conservatively. Consents are not changed; staff decide.

## 11. Event contract

Published (ids only), deduped per follow-up, version and status. The correlation id is carried from the triggering event.

| Event | When |
|---|---|
| `follow_up.human_review_required` | Draft awaiting approval |
| `follow_up.handed_off` | Task created or linked |
| `follow_up.scheduled` | Approved with a connected provider |
| `follow_up.sent` | Sent manually or provider accepted |
| `follow_up.suppressed` | Blocked by policy |
| `follow_up.cancelled` | Cancelled |
| `follow_up.expired` | Expired |
| `follow_up.failed` | Failed |

`follow_up.delivered` is never emitted: there are no delivery webhooks.

Consumed (`follow_up_agent`):
- `property_matching.completed` (Agent 04's own consumer row);
- `lead.qualification.needs_information`, `voice_call.completed`, `voice_call.human_handoff_requested` and `lead.communication_opted_out`, through the fan-out trigger (`dedupe fu_fanout:<event id>`).

## 13. Setup and operations

- **Nothing to start.** `follow-up-tick` (SQL) and `follow-up-worker` (Edge Function; URL + secret in Vault) run every minute.
- **Claude drafting (optional):** `ANTHROPIC_API_KEY` as an Edge Function secret (optionally `FOLLOW_UP_MODEL`). Without it, template drafts are used.
- **Consent:** messages need `granted` consent for the channel (purpose `service`; re-engagement needs `marketing`). Record it on the contact or at lead creation; unknown is never permission.
- **Sending today:** lead → Calls & messages → review → **Approve this version** → **Copy text** → send it yourself → **Mark as sent** (policy re-checked; refused outside the window or limits).
- **Adding a provider later:**
  1. Add an adapter in `follow-up-delivery.ts` (`ADAPTERS[provider]`) using the provider's official API and its idempotency key support.
  2. Connect an `integrations` row (`integration_type` `messaging` / `email`, `status` `connected`, `configuration.channels`).
  3. Store credentials as Edge Function secrets.
  4. Add a delivery-webhook handler that maps provider ids → `follow_ups.provider_message_id` to set `delivered`.
- **Inspect:**
  - runs: `agent_runs` where `agent_id = 'follow_up_agent'`;
  - items: `follow_ups` (status, status_reason, policy);
  - events: `outbox_events` where `event_type like 'follow_up.%'`;
  - failed or ambiguous sends: `follow_ups` where `status = 'failed'`, plus their "Check whether a follow-up was delivered" tasks.

## 14. Limitations

- **Messaging:** no email / SMS / WhatsApp provider, so no automated sending and no delivery status. The dispatch path is ready but has no adapter.
- **Claude:** drafting has never run live.
- **Inbound replies:** none are captured. "Unanswered" means no human or call contact since the messages were sent.
- **Time zones:** contacts have no time zone; the org time zone is used.
- **Appointments:** confirmation and reschedule messages are left to Agent 06.
- **Settings:** no settings screen; use `follow_up_settings_save`.
- **Retention:** sent message text is kept on the follow-up and the timeline, with no retention policy yet.
- **Test data:** remains in the E2E Realty A/B test workspaces.
